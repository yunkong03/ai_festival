# 코퍼스 커버리지 전략 (Master Matrix)

> 이 문서는 "우리 코퍼스의 어느 부분을 어떤 방식으로 지원하는가"의 단일 참조표다. `hybrid_architecture_proposal.md` §4가 이 문서를 요약 인용하고, `team_workstreams.md`/`development_roadmap.md`의 정밀 지원 착수 순서가 이 문서의 "정밀 지원" 열을 그대로 따른다.

## 0. 확인된 사실 / 추정 / 회의 결정 사항 구분

이 문서(및 다른 기획 문서)의 서술은 아래 3단계로 라벨링한다. **[확인]** 표시가 없는 수치·구조 주장은 아직 검증되지 않은 추정이므로 구현 전에 반드시 원문으로 확인한다.

### 0.2 [추정] — 근거는 있으나 미검증, 구현 전 확인 필요

- 정기공시 재무제표 3계정(매출액/영업이익/당기순이익)의 표 내 라벨이 70개사·13분기에 걸쳐 일정할 것 — **금융지주(KB금융·신한지주 등)는 계정과목 체계가 다를 가능성이 높음**, 표본 확인 필요
- 주요사항보고서 각 유형의 라벨-값 구조가 유형 내에서는 일정할 것
- 거래소공시 KIND xforms의 "마지막 셀 = 값" 휴리스틱이 3종 외 유형에도 통할 것

### 0.3 [회의 결정] — 사실이 아니라 팀이 정해야 하는 것

`meeting_decisions.md` 참조. 대표적으로: BM25 엔진 선택, 자기주식 공시의 정밀 지원 여부, 지분공시 지원 등급, **Dense 임베딩 모델 선택(BGE-M3 vs multilingual-e5, [확인] 둘 다 공식 허용됨 — 어느 쪽을 쓸지만 팀 결정 사항)**.

## 1. 3단계 정의

| 단계 | 정의 | 만드는 것 |
|---|---|---|
| **정밀 지원** | 반복적·구조가 일정하며 숫자·날짜·비율의 정확도가 중요한 항목 | 전용 Parser + Fact Extractor + Event Resolver + Python Calculator |
| **범용 RAG 지원** | 전용 Fact Extractor는 만들지 않지만 문서·섹션·표·문단을 검색해 근거 기반 자연어 답변 생성 | 구조 보존 Chunk(SECTION/TABLE/PARAGRAPH) + BM25(+가능하면 Dense/RRF) 색인 |
| **지원 제한** | (a) 코퍼스 밖 기업·기간·외부 정보 요구 (b) 투자 추천 요구 (c) 원문 누락·파싱 불가 (d) 근거 부족 또는 질문이 모호 | LIMIT_OR_CLARIFICATION — 이 4가지 사유 외에는 사용하지 않는다 |

**금지 논리** (이전 버전 문서에서 발견되어 제거함, 다시 등장하면 안 됨): "참고 질의에 없으므로 제외" / "질의 빈도가 낮을 것 같으므로 제외" / "자유서술형이므로 제외" / "정형화가 어려우므로 질의 지원에서도 제외" / "우선순위가 낮으므로 파싱·색인하지 않음". 이 중 어느 것도 "지원 제한"의 4대 사유가 아니다 — 정형화(정밀 지원)를 안 하는 이유는 될 수 있어도, 검색(범용 RAG 지원)까지 빼는 이유는 될 수 없다.

### 2.3 주요사항보고서 (major, 598건)

**선행 필수 작업 [확인]**: `major`의 `doc_subtype`은 **598건 전부 빈 문자열**이다. Metadata Filter가 동작하려면 `report_nm`(예: `주요사항보고서(유상증자결정)`)에서 **파생 subtype을 만들어 `DocumentRecord.derived_subtype`에 채워야 한다**(`interface_contract_draft.md` §1). 이것은 major 관련 모든 정밀 지원의 전제조건이며 난이도는 낮다(정규식 1개) — 하지만 없으면 major 전체가 metadata로 걸러지지 않는다.

**우선순위 재조정 근거 [확인]**: 이전 버전은 Q4 예시(유상증자/CB/BW/EB)만 정밀 지원 대상으로 삼았으나 그 4종 합계는 **82건(13.7%)**뿐이다. 반면 자기주식 관련이 **338건(56.5%)**로 major의 과반이고, 상각형조건부자본증권(71건)은 CB(22건)의 3배다. 참고 질의 예시에 맞춰 정밀 지원을 짜면 major의 절반 이상이 정밀 경로에서 빠진다 — 실제 분포 기준으로 재배치한다.

| 섹션/항목 | 건수 | 지원 수준 | 비고 |
|---|---|---|---|
| **자기주식 취득/처분/신탁계약 결정** — 취득·처분 주식수, 금액, 기간 | **338** | **정밀 지원 (1차, 신규 승격)** | major 과반. 구조 반복적, 금액·수량 명확. 이전 버전이 누락했던 최대 누락분 |
| 유상증자 결정 — 발행금액, 목적, 청약일/납입일 | 56 | 정밀 지원 (2차) | Q4 직결 |

- `revenue_consolidated_krw`, `operating_profit_consolidated_krw`, `net_income_consolidated_krw` (정기공시, 신규 — 연결기준 3계정, 별도기준은 여유 있을 때 확장)
- `treasury_stock_amount_krw`, `treasury_stock_shares` (주요사항보고서 자기주식 — **1차, 338건으로 major 최대**)
- `rights_offering_amount_krw` (유상증자 56건, 2차), `contingent_capital_amount_krw` (상각형조건부자본증권 71건, 3차), `cb_issue_amount_krw` (22건, 4차)
- `original_submission_date` (정정 연결용, 기존 계획)
- `holding_total_shares`, `holding_total_pct`, `holding_report_date` (지분공시 — **합계 행 한정**, §2.4)

**의도적으로 만들지 않는 fact_type**: `bw_issue_amount_krw`(**코퍼스 0건**), `eb_issue_amount_krw`(4건), `asset_acquisition_amount_krw`(5건) — 건수 대비 비용이 맞지 않는다. 해당 질의는 범용 RAG 경로로 답하거나, BW의 경우 "공시 없음"을 명시한다.

## 4. Fallback 정책

`hybrid_architecture_proposal.md` §3에서 정의한 순서를 그대로 따른다:

1. **FACT_LOOKUP 우선 시도** — 질의가 요구하는 `fact_type`이 §3의 핵심 Fact 목록에 있고 해당 문서가 정밀 지원 완료 상태면 여기서 답이 나온다.
2. **실패 시 EVIDENCE_SUMMARY로 fallback** — 같은 `doc_id`/`doc_subtype` 범위에서 BM25(+가능하면 Dense) 검색으로 관련 chunk를 찾아 HyperCLOVA X가 근거 기반 서술 답변을 생성한다. 정밀 지원이 아직 없는 항목(BW/EB, 지분공시 세부, 재무제표 주석 등)은 **항상 이 경로로 대응 가능**해야 한다.
3. **그래도 근거가 없으면 LIMIT_OR_CLARIFICATION** — §1의 4대 사유 중 하나로 명시적으로 한계를 고지하거나 역질문한다.

이 3단계가 있어야 "정밀 지원이 안 된 = 대답 못 함"이 아니라 "정밀 지원이 안 된 = 조금 더 서술적으로 대답함"이 된다.

## 5. 구현 난이도와 일정 축소 순서

`development_roadmap.md`의 "일정이 부족할 때의 축소 순서"와 동일 원칙, 여기서는 코퍼스 커버리지 관점으로 재정리:

**난이도 재평가 [확인]**: 이전 버전은 "전체 BM25 색인 = 난이도 중"으로 봤다. 실측 코퍼스가 **5.29GB(periodic 95%, 평균 3.44MB/최대 30.7MB per XML)**임이 확인되어 **난이도 상**으로 상향한다. 이는 라이브러리 선택을 좌우한다 — `rank_bm25` 같은 순수 파이썬 인메모리 구현은 이 규모에서 실용적이지 않으며, **SQLite FTS5 / Tantivy / Lucene 계열의 디스크 기반 역색인**이 필요하다(회의 결정 사항).

| 우선순위 | 항목 | 난이도 | 일정 부족 시 |
|---|---|---|---|
| 1 (최우선, 항상 유지) | 4개 doc_group 전체 SECTION/TABLE/PARAGRAPH chunk 생성 + **전체 BM25 색인** | **상**(5.29GB) | 자르지 않음 |
| 1.5 (최우선, 항상 유지) | **Metadata Filter + 계층형 축소(문서→섹션→청크)** | 중 | 자르지 않음 — **5GB 규모에서는 품질 개선이 아니라 검색을 가능하게 만드는 전제조건**(§아래) |
| 2 (MVP 필수) | 거래소공시 3종 Fact Store, 정기공시 재무 3계정, Citation | 중(연결/별도는 섹션 제목으로 해결 — 난이도 하향) | 자르지 않음 |
| 3 (여유 있을 때) | major 정밀 지원(자기주식→유상증자→상각형→CB), 지분공시 합계행 정밀화 | 상(유형 다양) | 뒤에서부터 미루되 해당 문서의 RAG 검색은 유지 |
| 4 (가능하면 추가) | **Dense Retrieval(1단계 4개 섹션 한정) + RRF**, Context Bundling | 중~상(**임베딩 대상 규모가 문제**) | **[확인] 규정상 허용(BGE-M3/multilingual-e5), 다만 전체 5GB 즉시 임베딩은 비현실적** — 1단계 범위만 적용하고 Recall 개선 확인 전엔 확대 안 함(§아래). 부족하면 1단계도 스킵 |
| 5 (Post-MVP) | Cross-Encoder Re-ranking, Query Decomposition | 상 | 예선 이후로 미룸 |
| 6 (실험 트랙, 게이팅) | Hard Negative, HyDE, Dynamic N-shot, DPO Reranker | 상~매우상 | 5주 로드맵에 아예 배치하지 않음 |

### 계층형 검색을 "가능하면 추가"에서 "MVP 필수"로 올린 이유

5.29GB / 수십만 청크 규모에서 **flat 검색은 품질 이전에 응답 지연·메모리 측면에서 성립하지 않는다.** metadata로 문서를 수 건까지 줄이고 그 안에서 섹션→청크로 좁히는 구조가 있어야 검색이 실용 속도로 동작한다. 즉 계층형은 정확도 옵션이 아니라 **규모 대응 필수 설계**다. 또한 `evaluation_strategy.md`의 Document/Section/Evidence Recall@k는 계층 구조가 있어야 측정 가능하므로, 계층형을 옵션으로 두면 핵심 평가 지표를 잴 수 없다는 모순도 생긴다.

### Dense Retrieval — 규정 확인 및 단계적 적용 근거

**[확인 — 주최 측 공식 답변]** 제공 코퍼스 외 문서를 답변 근거로 쓰는 것은 금지되지만, Dense Retrieval 자체와 **BGE-M3·multilingual-e5 등 사전학습 임베딩 모델을 검색 도구로 쓰는 것은 규정상 허용**된다. 단 임베딩·검색 대상은 제공 코퍼스로 제한하고 최종 답변 생성은 HyperCLOVA X만 사용한다 — 이는 "규정상 배제"가 아니라 순수 리소스 문제였다는 뜻이다.

그럼에도 5GB 전체를 한 번에 임베딩하면 청크 수가 수십만~수백만 규모가 되어 (a) 임베딩 호출 비용·시간이 5주 일정과 크레딧 한도를 위협하고 (b) 3인 팀이 벡터 인덱스 운영까지 감당하기 어렵다. 따라서 **주최 측이 제시한 단계적 적용**을 그대로 채택한다: **1단계 — periodic의 사업내용(사업의 개요·주요 제품 및 서비스)·원재료 및 생산설비·위험요인·연구개발활동 섹션**(Open-ended 질의 비중이 높은 구간)에만 적용해 BM25+RRF로 결합. **2단계 — 1단계에서 Recall 개선이 실측 확인될 때만** 다른 섹션·doc_group으로 확대. 확대 여부의 기준이 "여유가 있는가"가 아니라 **"효과가 측정됐는가"**라는 점이 핵심이며, 이것은 "커버리지 축소"가 아니다 — BM25가 이미 전체를 커버하므로 Dense는 그 위에 조건부로 얹는 품질 보강일 뿐이다.

**핵심 원칙**: 1·1.5번은 3~6번이 전부 취소되더라도 유지되어야 하는 바닥선이다. 이것이 무너지면 "정밀 지원이 없는 코퍼스 절반이 사실상 서비스되지 않는" 이전 버전의 실수로 되돌아간다.
