# 평가 전략 — 공식 기준 정리 + 내부 지표 매핑

## 1. 공식 평가 절차 (PDF p.6)

**예선** (~09.06 제출, 평가 09.07~09.30): 정량 + 정성 혼합 종합평가.

- **정량평가**: 참가팀이 준비한 평가용 API End-point(`GET /answer`)에 주최 측이 GET 요청 → 비공개 평가문제에 대한 답변 호출 → 평가. 평가문제는 **난이도 상/중/하 × Closed/Open-ended 혼합**.
- **정성평가**: 주제별 기술·도메인 전문가 검토. 항목: 문제정의 / 기술완성도·성능 / 창의성·확장성 / 답변의 정확성·완결성 / 현업 활용성·리스크 관리.

**결선** (최종 본선 진출 6팀): PT + 라이브 시연 중심, 평가위원 현장 종합평가.

**서버 운영 필수 기간**: 09.07~09.20 반드시 API 활성화 유지 — 이 기간에 서버가 죽어 있으면 정량평가 자체를 못 받는다(가장 치명적인 실패 모드).

## 2. 평가지표 8종 → 내부 지표 매핑

각 지표를 "무엇으로 담보하는가"와 "어떻게 스스로 측정하는가"로 분해한다.

| 공식 지표 | 담보 컴포넌트 | Workstream | 내부 측정 방법 |
|---|---|---|---|
| 정확성(수치·사실·비교) | `ExtractedFact` Python 파싱 + `CalculationRecord` | A, C | 단위테스트 통과율, PoC 기준선(투자금액 5/5, 계약금액 5/5) 유지 여부, 회귀 시 즉시 감지 |
| 근거완전성 | `RetrievalResult.facts`/`chunks`가 질의의 모든 요구사항을 커버 | B | eval set 기준 recall(질의당 "반드시 나와야 하는 근거"를 사람이 미리 라벨링) |
| 요구사항충족 | `TaskPlan.routes`가 질의의 모든 sub-ask를 커버(예: Q4의 "유형별로") | B, C | 체크리스트 기반 완결성 점검(질의 파싱 시 sub-ask 목록화 → answer에 전부 반영됐는지 대조) |
| 근거기반(hallucination 방지) | `VerificationResult.hallucination_flag` | C | `unsupported_claims` 개수 0 목표, 적대적 질의(근거 없는 사실 요구)로 자체 테스트 |
| 추론논리성 | `think_trace`의 구조화된 실행기록 | C | 팀 내부 리뷰어가 무작위 샘플 answer의 think_trace를 읽고 "선택된 route가 질의와 논리적으로 맞는가" 체크 |
| 안전성 및 신뢰성 | `VerificationResult.safety_flag`, 입력 sanitize | C | 프롬프트 인젝션·개인정보 요청 등 적대적 테스트셋 통과율 |
| 정보한계대응 | LIMIT_OR_CLARIFICATION 경로 | B, C | 기간 밖(2026.04 이후)/비대상 기업/근거 부족 질의를 의도적으로 넣어 100% 정확히 한계 고지하는지 확인 |
| 근거 공시 표시(전 답변 공통) | Citation | C | `answer`에 공시명·공시일이 없는 응답이 하나도 없는지 자동 검사 |

## 2.5 계층형 내부 지표 (Layered Metrics)

최종 답변 정확도 하나만 재면 오답의 원인(검색 실패인지, 추출 버그인지, 계산 버그인지, 생성 단계 hallucination인지)을 구분할 수 없다. XBRL Agent/FinQAPT/FinSage류 시스템의 평가 방식을 참고해 파이프라인 단계별로 지표를 분리 측정한다. `RetrievalResult.retrieval_trace`(`interface_contract_draft.md` §7)가 이 측정의 원재료다.

| 지표 | 정의 | 측정 단계 | 담당 |
|---|---|---|---|
| Document Recall@k | metadata 필터링 후 후보 문서 집합에 정답 문서(`rcept_no`)가 포함되는 비율 | §7.2 문서 단계 | B |
| Section Recall@k | 섹션 단위 검색에서 정답 섹션이 상위 k에 포함되는 비율 | §7.2 섹션 단계 | B |
| Evidence Recall@k | 최종 evidence(cell/문장) 단위에서 정답 근거가 상위 k에 포함되는 비율 | §7.2 evidence 단계 | B |
| Fact Extraction Accuracy | `ExtractedFact.value`가 원문과 정확히 일치하는 비율 | A의 파서/추출기 | A |
| Calculation Accuracy | `CalculationRecord.result`가 수학적으로 정확한 비율(순수 Python이므로 버그가 없으면 이론상 100%에 근접해야 함 — 100% 미만이면 버그) | C의 Calculator | C |
| Citation Accuracy | `answer`에 표시된 근거가 실제로 해당 주장을 뒷받침하는 비율 | C의 Verifier/Citation | C |
| Final Answer Accuracy | 공식 "정확성" 지표에 대응하는 end-to-end 정확도 | 전체 파이프라인 | 전체 |

**[확인 — 주최 측 공식 답변] Dense Retrieval 도입 게이트**: Dense Retrieval은 규정상 허용되고 임베딩 모델은 BGE-M3·multilingual-e5 등 자유 선택이지만, periodic의 사업내용·원재료 및 생산설비·위험요인·연구개발활동 섹션에 **1단계 적용한 뒤 BM25-only 대비 Section/Evidence Recall@k가 실제로 개선되는지**를 반드시 측정한다. 개선이 확인되지 않으면 다른 섹션·doc_group으로 확대하지 않는다 — Dense 확대는 "여유가 있으면"이 아니라 "이 지표가 개선됐으면"으로 게이팅한다(`hybrid_architecture_proposal.md` §7.3, `corpus_coverage_strategy.md` §5).

**측정 우선순위**: Document/Section/Evidence Recall@k는 계층형 Retrieval 구조를 전제로 하는데, 계층형이 **MVP 필수로 상향**되었으므로(`hybrid_architecture_proposal.md` §5.1, §7.2) 이 3개 지표는 MVP 범위 안에서 측정 가능하다. (이전 버전은 계층형을 "가능하면 추가"로 두면서 이 지표들을 핵심 지표로 삼아 **모순**이었다 — 계층형이 빠지면 핵심 평가 지표를 잴 수단이 사라졌다. 등급 상향으로 해소.) Fact/Calculation/Citation Accuracy는 각 Workstream이 자기 컴포넌트 단위테스트로 Week 1~2부터 선행 측정한다. **컴포넌트별 지표를 먼저 확보해야 Final Answer Accuracy가 낮을 때 어디를 고칠지 바로 알 수 있다** — 이것이 평가 인프라를 "먼저" 만들어야 하는 이유다.

## 3. 내부 평가(eval) 데이터셋 제작 계획

공식 평가문제는 비공개이므로, 팀 자체 eval set이 유일한 사전 검증 수단이다.

- **원천**: 공식 참고 질의 6종 유형(`official_requirements_gap.md` §2)을 각각 실제 코퍼스 기업/연도로 구체화 — 예: Q1은 "삼성전자의 2024년 연결기준 매출액은?" 처럼 실제 존재하는 문서로 만든다.
- **[중요] 6종 예시에 과적합하지 않기 위한 할당 규칙**: eval set의 **절반 이하만** 공식 6종 유형을 모사하고, **나머지 절반 이상은 코퍼스 실제 분포에서 뽑는다.** 근거: 실측 결과 참고 질의가 지목한 대상과 코퍼스 실제 분포가 크게 어긋났다(`corpus_coverage_strategy.md` §0.1) — Q3가 지목한 2차전지 설비투자는 LG에너지솔루션·삼성SDI에 거래소공시가 0건이고, Q4가 나열한 BW는 코퍼스에 0건인 반면 major의 과반(338건)은 예시에 없는 자기주식 공시다. 6종만 모사한 eval set은 **우리가 실제로 못 하는 것을 못 잡아낸다.** 구체적 할당:
  - 문서유형 비례 배분: periodic / exchange / major / holding 각각에서 최소 몇 문항씩(건수 비중 반영)
  - major는 **자기주식(338건)·상각형조건부자본증권(71건)** 등 실제 최다 유형 질의를 반드시 포함
  - 정기공시는 재무 3계정 외에 **위험요인·연구개발·원재료 및 생산설비·임원보수·재무제표 주석** 질의 포함
  - 지분공시 질의(보고자·지분율·변동사유) 포함
- **정답 라벨링**: 각 질의에 대해 (a) 기대 answer 값, (b) 정답 문서(`rcept_no`), (c) 정답 섹션(해당 시), (d) 반드시 포함되어야 할 evidence_id를 사람이 직접 원문에서 확인해 기록 — §2.5의 Document/Section/Evidence Recall@k를 측정하려면 최종 답변 하나만이 아니라 **이 계층별 정답을 전부 라벨링**해야 한다. 정형 수치 질의는 A가 Fact Store를 돌려 직접 만들 수 있음(자기 검증이므로 이중 확인 필요).
- **난이도 분포**: 공식 문제 구성(상/중/하 × Closed/Open)을 모사 — 특히 Open-ended·복합문서추론(Q4, Q6급)은 하 난이도가 아니므로 eval set에도 반드시 포함.
- **정보한계 케이스**: 코퍼스 밖 질문(2026.04 이후, 코퍼스에 없는 기업, "투자해도 될까요?" 같은 투자의견 요청)을 의도적으로 eval set에 섞는다 — 이건 팀이 스스로 만들지 않으면 아무도 안 만든다.
- **[확인] "코퍼스 안에 있지만 데이터가 없는" 케이스 — 별도 분류로 반드시 포함**: 위 "코퍼스 밖"과 다른 유형이다. 대상 기업·기간 안에 있는데 그 항목의 공시가 존재하지 않는 경우로, 오답 위험이 가장 크다(모델이 억지로 지어내기 쉬움). 실측으로 확인된 케이스:
  - **"OO기업의 BW(신주인수권부사채) 발행 내역"** → 코퍼스 전체에 **0건**. 정답은 "해당 기간 중 BW 발행 공시가 확인되지 않음"
  - **"LG에너지솔루션의 신규시설투자 공시상 투자금액"** → 해당 기업 신규시설투자등 **0건**. 정답은 "해당 공시 없음" + (가능하면) 정기공시 설비투자 서술로 대체 안내
  - **공급계약이 없는 37개사**에 대한 계약금액 질의
  이 케이스들은 "정보한계대응" 평가 항목의 실전이며, LIMIT_OR_CLARIFICATION이 **코퍼스 밖(기간/기업)뿐 아니라 "데이터 없음"까지 구분해 응답**하는지 검증한다.
- **관리**: 공동 책임(`team_workstreams.md`의 "공동 책임" 항목) — B가 도구(질의 실행+채점 스크립트)를 만들고 3인이 각자 담당 문서유형에서 질의-정답 세트를 채운다. **eval set 질의는 참고 질의 6종 유형에만 국한하지 않는다** — §정기공시 재무주석, 지분공시 변동사유, 위험요인 등 범용 RAG 전용 섹션을 겨냥한 질의도 반드시 포함해 "정밀 지원이 없는 항목도 RAG로 답이 나오는지"를 검증한다.
- **회귀 방지**: eval set은 CI 또는 최소 매 마일스톤마다 재실행해 정확도 추이를 추적한다. 특히 `hybrid_architecture_proposal.md` §6-(1)(문단 chunker 추가) 같은 구조 변경 후 기존 PoC 기준선(거래소공시 5/5)이 깨지지 않는지 반드시 재확인.

## 4. 결선 대비 (참고용, 예선 통과 후)
