# 아키텍처 방향 제안: A/B/C 비교 및 Hybrid 채택안

> 전제: `official_requirements_gap.md`의 갭 분석 결과를 기반으로 함. 이 문서는 방향 결정용이며 코드 구현을 포함하지 않는다.
>
> **주의**: 아래에서 Q1~Q6로 인용하는 공식 참고 질의 6종은 **예시일 뿐**, 실제(비공개) 평가셋의 전체 범위가 아니다. "Q1~Q6에 대응한다"는 서술은 "이 정도 유형에는 이 구조로 답할 수 있다는 근거"로 읽어야지, "코퍼스의 나머지는 안 물어본다"는 뜻으로 읽으면 안 된다 — §4에서 이 오독을 바로잡는다.

## 1. 세 방향 비교

### A. 거래소공시 3종 집중 Fact Store Agent

기존 계획(`2026-07-29-mvp-fact-store.md`) 그대로. `exchange` doc_group 3개 subtype(1,169건)만 정형 추출.

- 장점: PoC로 정확도 검증됨(투자금액 5/5, 계약금액 5/5). Evidence 완전 추적. 구현 리스크 낮음 — 3인 팀이 5주 안에 안정적으로 완성 가능.
- 단점: 참고 질의 6개 중 4개(Q1, Q2, Q4, Q6)에 **원천적으로 응답 불가**. "종합적으로 이해하고 비교·분석·설명"이라는 과제 핵심 문구, "정보 추출: 사업·재무·투자·계약·자금조달·지분변동 등"(PDF p.4)이라는 명시적 범위와 정면으로 어긋남. 정성평가 "문제정의" 항목에서 큰 감점 위험.

### B. 전체 4,204건 대상 범용 RAG Agent

모든 문서를 청킹→임베딩→검색, LLM이 답변 생성.

- 장점: 커버리지 최대. Q2, Q6 같은 서술형 질의에 자연스럽게 대응.
- 단점: **정확성**·**근거기반(hallucination 방지)** 평가축에서 구조적으로 불리. 재무제표처럼 숫자가 밀집된 표는 임베딩 유사도 검색이 정확한 셀을 못 찾을 위험이 높고, HyperCLOVA X 하나로 수치 비교·증감률까지 생성시키면 산술 오류·hallucination 리스크가 커짐. Q1("연결기준 매출액이 얼마인가")처럼 **하나의 정답 숫자**를 요구하는 Closed 질의에 RAG-only 파이프라인은 특히 취약하다. 3인 팀이 4,204건 전체를 안정적 품질로 처리(정정공시 처리, 표 구조 보존 등)하며 평가 가능한 상태로 5주 안에 완성하는 것도 일정 리스크가 크다.

### C. Hybrid — 핵심 수치는 정형 추출, 나머지는 구조 보존 RAG

- 장점: 정확한 수치가 필요한 질의(Q1, Q3, 대부분의 Q5, Q4의 금액 부분)는 정형 Fact Store로 정확도를 담보하고, 서술형·비교·요약 질의(Q2, Q4의 목적 서술, Q6)는 구조를 보존한 RAG + HyperCLOVA X 요약으로 커버한다. 이는 평가지표 8개 전부에 대응 가능한 유일한 구조다: 정확성=Fact Store, 근거완전성/근거기반=Evidence+Citation, 요구사항충족=Task Router의 경로 조합, 추론논리성=구조화된 실행기록(think_trace), 안전성=Verifier, 정보한계대응=전용 가드레일. 또한 3인 팀 구조(A/B/C)가 이미 이 아키텍처의 3개 축(추출/검색/생성)에 자연스럽게 대응된다.
- 단점: 가장 복잡하고 통합 리스크가 크다. Query Analyzer, Task Router, Verifier 등 신규 컴포넌트가 여럿 필요하고 5주 일정이 촉박하다.

## 2. 최종 권장: **C. Hybrid**

**근거:**
1. 공식 PDF가 "단순 키워드 검색을 넘어 여러 공시를 종합적으로 이해하고 비교·분석·설명하는 Agent 구현이 핵심"이라고 명시 — A만으로는 이 핵심 요구를 충족하지 못한다(Gap 분석 참조).
2. 평가지표 8개는 정형추출 강점 축(정확성, 근거기반)과 서술형 강점 축(요구사항충족, 추론논리성)을 동시에 요구한다. B는 전자에서, A는 커버리지 측면에서 각각 무너진다.
3. 검증된 PoC(투자금액 5/5, 계약금액 5/5)와 이미 작성된 Fact Store 계획은 **버리지 않는다** — Hybrid의 FACT_LOOKUP 경로 핵심 자산으로 그대로 Workstream A에 편입된다.
4. 3인 팀 규모가 정확히 3개 실행 축(추출·검색·생성)에 대응해 병렬 개발이 가능하다.

**전제 조건**: Hybrid를 채택하려면 팀 3명 모두 "각자 완결된 기능 하나"가 아니라 "하나의 파이프라인의 한 구간"을 만든다는 점에 동의해야 한다. 이는 `interface_contract_draft.md`의 계약을 첫 회의에서 확정하는 것이 전제다.

## 3. 실행 경로 4종 설계

| 경로 | 역할 | 주 소비 데이터 |
|---|---|---|
| FACT_LOOKUP | 정확한 수치·날짜·비율·상태 조회 | ExtractedFact (Workstream A) |
| EVIDENCE_SUMMARY | 사업/반기/분기보고서 등 비정형 내용 요약 | Chunk(문단) + HyperCLOVA X |
| MULTI_DOCUMENT_ANALYSIS | 기업 비교, 연도 비교, 정정 이력, 계약체결후해지, 다건 집계 | ExtractedFact + FilingEvent + VersionResolutionResult |
| LIMIT_OR_CLARIFICATION | 기간/기업 밖, 근거 부족, 투자의견 요청, 모호 질문 처리 | RetrievalQuery 분석 결과 + Verifier 판정 |

### 독립 Agent로 분리할 필요가 있는가 — **아니오**

4개는 별도 프로세스/엔드포인트가 아니라 **하나의 Task Router가 조합하는 실행 가능한 Capability(모듈/함수)**로 설계한다. 질의 하나가 여러 경로를 동시에 요구하는 경우가 실제로 다수다:

- Q5("계약체결후해지 여부")는 FACT_LOOKUP(계약명·금액 추출)과 MULTI_DOCUMENT_ANALYSIS(체결→해지 이력 연결)를 **모두** 필요로 한다.
- Q4("자금조달 내역 유형별 정리")는 FACT_LOOKUP(유형별 금액)과 EVIDENCE_SUMMARY(조달 목적 서술)의 조합이 자연스럽다.
- LIMIT_OR_CLARIFICATION은 파이프라인 어느 지점에서든(질의 분석 직후 즉시 판단 가능한 경우 — 예: 2026.04 이후 질문 — 도 있고, FACT_LOOKUP/EVIDENCE_SUMMARY 실행 후 근거 부족이 드러나는 경우도 있음) 트리거될 수 있는 **공용 가드레일**에 가깝다.

따라서 아키텍처는 "1개 Orchestrator(TaskPlan 생성) + 4개 Executable Capability + 1개 Synthesizer"로 구성하고, 질의 하나가 `TaskPlan.routes`에 여러 경로를 담아 순차/병렬 실행 후 통합하는 구조로 설계한다.

**정밀 경로 실패 시 범용 RAG로 fallback한다.** FACT_LOOKUP이 요청된 `fact_type`에 대응하는 `ExtractedFact`를 찾지 못하면(예: 아직 정밀 지원이 안 된 BW/EB 자금조달, 또는 지분공시 세부 취득 내역) 즉시 "확인할 수 없음"으로 답하지 않는다 — 같은 문서/같은 doc_subtype 범위에서 EVIDENCE_SUMMARY 경로(BM25 검색)로 한 번 더 시도한 뒤, 그래도 근거가 없으면 그때 LIMIT_OR_CLARIFICATION으로 넘어간다. 이 fallback 순서(FACT_LOOKUP 실패 → EVIDENCE_SUMMARY 시도 → 그래도 없으면 LIMIT_OR_CLARIFICATION)가 §4의 "정밀 지원이 아직 없어도 검색은 가능해야 한다" 원칙을 실행 단계에서 구현하는 방법이다.

**자유형 ReAct는 기본안으로 채택하지 않는다.** ReAct(관찰→사고→행동을 매 스텝 LLM이 즉흥적으로 결정하는 방식)는 실행 경로가 비결정적이라 (a) 재현성이 떨어지고 (b) 공식 API의 `think_trace`가 요구하는 "구조화된 실행 기록"과 정합이 나쁘며(원시 LLM 추론을 그대로 넣게 되기 쉬움) (c) 매 스텝 LLM 호출이 늘어 "HyperCLOVA X 최소 사용" 원칙과 충돌하고 (d) 프롬프트 인젝션에 노출되는 표면적이 넓어져 안전성 평가축에서 불리하다. 대신 Task Router가 질의 분석 시점에 필요한 route 조합과 실행 순서를 `TaskPlan.steps`로 **미리 확정**하고, Synthesizer는 그 계획을 그대로 실행한다 — 계획 수립과 실행을 분리하는 것이 XBRL Agent/FinQAPT/FinSage류 재무 문서 QA 시스템들이 공통적으로 채택한 구조다.

## 4. 문서 유형별 지원 수준 — 3단계 분류

**수정 이력**: 이전 버전은 "반드시 정형화 / RAG로 처리 / MVP에서 제외"로 구분했다. 이는 잘못된 프레이밍이었다 — "MVP 제외"라는 이름 아래 "참고 질의 6종에 없으므로", "질의 빈도가 낮을 것 같으므로", "자유서술형이므로"라는 이유로 **검색 자체를 포기**하는 항목이 섞여 있었다. 공식 PDF의 참고 질의 6종은 **예시일 뿐**이며(p.7 "참고용 질의 set는 참가팀의 이해를 돕기 위한 참고자료입니다. 실제 평가 데이터셋 및 세부 평가기준은 비공개") 비공개 평가셋이 코퍼스의 다른 항목(예: 지분공시 변동사유, 위험요인, 연구개발활동 등)을 직접 물을 가능성을 배제할 수 없다. 아래는 이를 바로잡은 최종 분류이며, 상세 매트릭스는 `corpus_coverage_strategy.md`에 정리한다.

### 3단계 정의

1. **정밀 지원**: 반복적·구조 일정·수치/날짜/비율 정확도가 중요한 항목. 전용 Parser + Fact Extractor + Event Resolver + Python Calculator로 처리. (구 "반드시 정형화"와 동일 범위)
2. **범용 RAG 지원**: 전용 Fact Extractor는 만들지 않지만 문서·섹션·표·문단 단위로 검색 가능하게 하고 근거 기반 자연어 답변을 생성한다. **"정형화 제외"이지 "질의 지원 제외"가 아니다.** (구 "RAG로 처리"에 구 "MVP 제외" 대부분이 흡수됨)
3. **지원 제한**: 코퍼스 밖 기업·기간·외부 정보 요구, 투자 추천 요구, 원문 자체가 누락되었거나 파싱 불가한 경우, 근거가 부족하거나 질문이 모호한 경우. **이 4가지 사유 외에는 어떤 문서·섹션도 "지원 제한"으로 분류하지 않는다.**

**전체 커버리지 원칙**: 가능한 모든 XML 문서는 최소한 범용 RAG 검색 대상에 포함한다. 최소 검색 가능해야 하는 정보: 기업·기간·doc_group/doc_subtype, 섹션 제목과 계층, 문단, 표 제목·행/열 헤더·값·단위, `is_correction`(정정 여부), `doc_id`/`evidence_id`/원문 위치. 전체 문서를 Fact Store로 만드는 것은 아니다 — 핵심 Fact만 정밀 지원하고 나머지는 구조 보존 RAG로 처리한다.

| 범용 RAG 지원 | **EB(4건)·자산양수도(5건)** 등 건수가 적어 전용 추출기 투자 대비 효과가 낮은 유형, 합병·분할·감자 등 소량 다품종 유형, 외부평가 세부 절차, 주식매수청구권 세부조건, 자유서술 전반 — 정밀 Fact Extractor가 없어도 문서 자체는 검색 가능해야 "확인할 수 없음" 대신 원문 근거로 답할 수 있다 |
| 해당 없음 → LIMIT_OR_CLARIFICATION | **BW(신주인수권부사채) — [확인] 코퍼스 0건.** 공식 Q4가 BW를 명시하므로 "BW 발행 내역" 질의에는 **"해당 기간 중 BW 발행 공시가 없음"을 명시적으로 답한다.** 추출기를 만들 대상이 아니다 |

### 지분공시 (1,083건, 5% 보고)

| 구분 | 항목 |
|---|---|
| 정밀 지원(최소) | 보고자명, 보고구분(신규/변동), 보유주식수, 보유비율(%), 변동사유, 보고사유발생일 — 구조가 단순하고 반복적이라 최소 정밀 지원 대상으로 유지 |
| 범용 RAG 지원 | 세부 취득/처분 내역 서술, 변동사유 상세 텍스트 등 나머지 전부. 공식 참고 질의 6개에 지분공시가 직접 등장하지 않는다는 이유로 이전 버전은 "스킵"했으나, 이는 §4 도입부에서 지적한 잘못된 배제 논리다 — **스킵하지 않고 최소한 검색 대상에는 반드시 포함**한다 |
| 지원 제한 | 없음 |

구현 난이도·착수 순서는 별개 축이다 — "정밀 지원 착수가 늦다"와 "검색도 안 한다"를 혼동하지 않는다. 착수 순서는 §5.2, 상세 매트릭스는 `corpus_coverage_strategy.md`.

## 5. MVP 우선순위와 정밀 지원 로드맵

### 5.1 우선순위 3단계 (구현 대상 vs 구현 시점)

§4의 "무엇을 지원하는가"(정밀/RAG/제한)와는 다른 축으로, "언제 만드는가"를 3단계로 나눈다. **일정이 부족해도 축소하는 것은 항상 아래쪽(Post-MVP)부터이며, 전체 문서 BM25 검색 커버리지는 어떤 상황에서도 유지한다.**

> **등급 재조정 [확인]** (`corpus_coverage_strategy.md` §0.1 실측 반영): 코퍼스가 **5.29GB(periodic 95%)**임이 확인되어 두 항목의 등급을 바꿨다. **계층형 Retrieval은 "가능하면 추가"→"MVP 필수"** (5GB flat 검색은 품질 이전에 성립하지 않음 + 계층 없으면 Recall@k 지표 자체를 못 잼). **Dense Retrieval은 "전체 적용"→"단계적 확대"** (5GB 전량 즉시 임베딩은 5주 일정·크레딧에서 비현실적이지만, 아래 [확인]대로 임베딩 모델 자체는 공식 허용되었으므로 배제가 아니라 **효과 검증 후 확대하는 단계적 롤아웃**으로 설계).
>
> **[확인 — 주최 측 공식 답변]** 제공 코퍼스 외 문서를 답변 근거로 쓰는 것은 금지되지만, **BGE-M3·multilingual-e5 등 사전학습 임베딩 모델을 검색 도구로 쓰는 것은 허용된다.** 단 임베딩·검색 대상은 제공 코퍼스로 제한하고 **최종 답변 생성은 HyperCLOVA X만** 사용한다. 즉 "HyperCLOVA X만 사용 가능"이라는 공식 제약은 **생성형 LLM(답변 생성)에만 적용**되고 임베딩 모델 선택에는 적용되지 않는다 — 이전 버전 문서 곳곳의 "임베딩까지 HyperCLOVA X 최소 사용 원칙과 충돌 여지"라는 서술은 이 확인으로 해소됐다.
>
> **주최 측이 명시한 Dense 도입 방식**: 전체 코퍼스에 일괄 적용하지 않는다. **periodic의 사업내용(사업의 개요·주요 제품 및 서비스)·원재료 및 생산설비·위험요인(위험관리 및 파생거래)·연구개발활동 섹션부터 적용**하고 BM25와 RRF로 결합한 뒤, **Recall 개선이 실측으로 확인될 때만** 범위를 확대한다. 이는 "가능하면 MVP에 추가"의 실행 순서 자체를 지정한 것이므로 아래 §5.1·§7.3에 그대로 반영한다.

### MVP 필수

1. 전체 XML **구조 보존 Parsing** — TABLE뿐 아니라 SECTION/PARAGRAPH chunk 생성, `section_hierarchy` 보존, 표는 제목·행/열헤더·단위·기준기간 보존(§7). **[확인] 연결/별도는 표 헤더가 아니라 섹션 제목(`2-2. 연결 포괄손익계산서`)으로 판별**
2. Metadata Filter (§7.1) — 검색 전 기업/기간/doc_group/**파생 subtype**/연결·별도로 후보 축소. **[확인] `major`의 `doc_subtype`은 598건 전부 빈 문자열이므로 `report_nm`에서 파생 subtype 생성이 선행 필수**
3. **전체 문서 BM25 검색** — 4,204건(5.29GB) 전부가 최소 BM25 색인 대상(§7.3). 이것이 "범용 RAG 지원"의 최소 구현체. **디스크 기반 역색인 엔진 필요**(SQLite FTS5/Tantivy/Lucene 계열 — 순수 파이썬 인메모리 BM25는 이 규모에서 부적합)
4. **계층형 축소(문서→섹션→청크)** — §7.2. 5GB 규모에서 검색을 성립시키는 전제조건
5. 기존 핵심 Fact Store(거래소공시 3종) + Python Calculator
6. HyperCLOVA X 근거 기반 답변 생성(EVIDENCE_SUMMARY 경로, BM25 검색 결과 기반)
7. Citation + 계층형 평가 지표(§`evaluation_strategy.md`)

### 가능하면 MVP에 추가

8. **Dense Retrieval (단계적 확대, [확인] 주최 측 공식 허용)** — **1단계**: periodic의 사업내용(사업의 개요·주요 제품 및 서비스)·원재료 및 생산설비·위험요인·연구개발활동 섹션에만 BGE-M3 또는 multilingual-e5(둘 다 사전학습 다국어 임베딩, 한국어 지원)로 임베딩해 BM25+RRF로 결합. **2단계**: 1단계에서 Recall@k 개선이 실측으로 확인되면 다른 섹션·doc_group으로 확대. 임베딩·검색 대상은 제공 코퍼스로 제한, 답변 생성은 여전히 HyperCLOVA X만. BM25가 이미 전체를 커버하므로 이것은 커버리지가 아니라 품질 보강이다
9. RRF (BM25+Dense 결합, 학습 불필요)
10. Context Bundling (구조적 결합, §7.4)

이 3개는 유효한 품질 개선이지만 **MVP 필수 baseline(BM25 전체 커버리지 + 계층형 축소)이 확보된 뒤에만** 순서대로 추가한다.

### Post-MVP

Cross-Encoder Re-ranking, Query Decomposition — §9. 그 뒤가 실험 트랙(Hard Negative, HyDE, Dynamic N-shot, DPO Re-ranker) — §10. 학습 기반·고도화 기법부터 먼저 잘라낸다.

### 5.2 MVP 정밀 지원 로드맵 (Fact/Event/Calculator 확장)

§4의 "정밀 지원" 항목을 실제로 만드는 순서. `corpus_coverage_strategy.md`의 매트릭스와 1:1 대응.

1. 거래소공시 3종 Fact Store (기존 계획 그대로, 완료 자산)
2. 정기공시 핵심 재무제표 계정 3종(매출액/영업이익/당기순이익, 연결기준) 정형 추출 → Q1
3. **`major` 파생 subtype 생성**(`report_nm` 정규식) — major 관련 모든 정밀·필터 작업의 전제, 난이도 낮음
4. 주요사항보고서 정밀 추출 — **실제 분포 기준 순서: 자기주식(338건) → 유상증자(56) → 상각형조건부자본증권(71) → CB(22)**. **[확인] BW는 코퍼스 0건이므로 추출기를 만들지 않고 "공시 없음" 응답으로 처리**, EB(4건)·자산양수도(5건)는 범용 RAG로
5. 계약명 기반 체결→해지 이벤트 연결 → Q5
6. 정정 후보 연결(CorrectionResolver, 기존 계획 확장 — §6-기술검토 참조)
7. 기업/연도 단위 단순 비교·집계(합산, 증감률) → Q3. **[확인] 단, 설비투자 비교는 거래소공시(21개사만 커버)로 불충분하므로 정기공시 `II-3. 원재료 및 생산설비` RAG와 병행해야 한다**
8. 지분공시 **합계 행 한정** 정밀 지원(대표 보고자/합계 주식수/합계 지분율) — 개별 특별관계자 행은 RAG
9. 모든 응답에 `evidence_id` 기반 Citation

**주의**: 위 순서는 "정밀 지원을 언제 늘리는가"이지 "언제부터 검색 가능한가"가 아니다. §5.1의 MVP 필수 1~3번(전체 문서 구조보존 파싱 + BM25 색인)은 이 순서와 무관하게 **가장 먼저, 전체 문서 대상으로** 끝내야 한다 — 정밀 지원 3번(주요사항보고서 자금조달)이 아직 안 됐어도 그 문서 자체는 1주차부터 BM25로 검색 가능해야 한다.

## 6. 기존 Fact Store 계획(`2026-07-29-mvp-fact-store.md`)에 대한 기술 검토

사용자 요청에 따라 6개 항목을 검토한다. **이 계획은 그대로 Workstream A의 시작점으로 유효**하지만 아래 항목은 실행 전 수정이 필요하다.

### (1) DartDocumentParser가 표뿐 아니라 문단/섹션을 검색 가능한 Chunk로 만드는가?

**아니오.** `Task 6`의 `DartDocumentParser._walk_tables`는 `TABLE` 엘리먼트만 순회한다. `<P>` 문단은 전혀 chunk화되지 않는다. 정기공시뿐 아니라 4개 doc_group 전체를 범용 RAG 지원 대상으로 삼으려면(§4) 문단/섹션 chunker가 **반드시 추가**되어야 한다 — 이는 정확히 §5.1 "MVP 필수 1번"(전체 XML 구조 보존 Parsing) 항목이며, `development_roadmap.md`에서 Workstream A의 Week 0~1 최우선 작업으로 배치한다.

이때 단순히 `<P>`를 순서대로 chunk화하는 것으로는 부족하다. §7의 계층형 Retrieval 원칙을 지원하려면 **원래 계획의 `Chunk` 스키마 자체를 확장**해야 한다:
- `Chunk.section_hierarchy: list[str]` — 문서→장→절 breadcrumb (예: `["사업의 내용", "1. 사업의 개요"]`). 지금의 `section_path`는 XML 태그명 나열이라 사람이 읽는 섹션 제목이 아니다 — `TITLE` 엘리먼트의 텍스트를 그대로 뽑아 breadcrumb으로 저장해야 Section Recall@k(§`evaluation_strategy.md`) 측정과 Context Bundling(§7)이 가능해진다.
- `Chunk.table_metadata: TableMetadata | None` (TABLE kind에만) — 표 제목, 행 헤더, 열 헤더, 단위, 기준기간, 연결/별도 여부. `interface_contract_draft.md`에 스키마 추가.

### (2) 날짜만 일치하는 정정 후보를 resolved로 확정해도 안전한가?

**부분적으로만 안전하다.** 현재 `CorrectionResolver`는 `(corp_code, doc_subtype, rcept_dt==추출된 최초제출일)` 3개 신호가 **유일하게** 일치할 때만 `resolved`를 반환하고, 후보가 여럿이면 `ambiguous`로 떨어지므로 "틀린 걸 확정"하지는 않는다. 하지만 원 스펙이 요구한 후보 신호(기업, 최초제출일, 정규화된 공시명, 공시 유형, **계약명/투자명**, 금액) 중 3개만 쓰고 있어, 동일 기업이 같은 날 같은 유형의 공시를 우연히 하나만 냈을 경우 계약명이 실제로 다른데도 `resolved`로 오판할 위험이 이론상 남는다. **권장**: `resolved` 승격 조건에 계약명/투자명(§4에서 신규 추출 예정) 일치를 2차 신호로 추가하거나, 최소한 팀 내부적으로 현재의 3-신호 `resolved`를 `probable`로 재정의하고 자동 최신본 교체는 `manually_resolved`에만 적용하는 보수적 정책을 채택한다.

### (3) "append-only" 설명과 FactStore의 덮어쓰기 구현이 충돌하는가?

**충돌한다 — 명명 오류.** 계획의 Global Constraints는 "append-only jsonl"이라 서술하지만 `Task 9`의 실제 구현은 `open(self.output_path, "w", ...)`로 **매 실행마다 파일을 덮어쓴다**(truncate). 버그는 아니다(오히려 재실행 시 매번 전체를 재계산하는 편이 5주 일정의 3인 팀에게는 더 단순하고 안전하다) — 하지만 이름과 실제 동작이 불일치하므로 **문서 정정**이 필요하다: "FactStore는 append-only가 아니라 실행마다 전체를 재계산·재기록하는 idempotent snapshot writer"로 재정의할 것을 권장한다. 진짜 증분(append) + 이력 보존이 필요해지면 그때 모드를 바꾸고 중복 제거 로직을 추가한다.

### (4) ID가 재파싱 후에도 안정적인가?

**표 순서가 유지되는 한 안정적이다.** `make_chunk_id`/`make_evidence_id`는 doc_id + 상대경로 + section_path + 테이블 전역 순번 + row/col로 결정론적이며, 이는 XML 문서 구조에서 항상 동일하게 재현된다(단위테스트로 검증됨). 다만 `_section_path_for`가 태그명만으로 경로를 구성하기 때문에 동일 태그의 형제 섹션이 여럿이면 문자열 자체의 사람이 읽는 의미는 약해질 수 있다(전역 테이블 순번이 실질적 유일성을 보장하므로 재현성 자체는 문제없음). 향후 개선 여지로만 기록.

### (5) placeholder나 잘못된 실제 경로가 남아 있는가?

## 7. Retrieval 아키텍처 원칙 (XBRL Agent / FinQAPT / FinSage 참고)

재무 문서 QA 시스템 설계·실험 결과(XBRL Agent, FinQAPT, FinSage)를 참고한 4가지 원칙. **모두 "학습이 필요 없는" 방식을 기본안으로 삼아 5주 일정에 맞춘다.** 단 4개의 구현 우선순위는 동일하지 않다 — §7.1(Metadata-First), §7.2(계층형 축소), §7.3의 **BM25 전체 커버리지**는 §5.1의 **MVP 필수**이고, §7.3의 **Dense+RRF 결합**과 §7.4(Context Bundling)는 **"가능하면 MVP에 추가"** 등급이다. 즉 Metadata 필터 + 계층형 축소 + BM25만으로 "범용 RAG 지원" 최소 요건(§4)이 충족되며, Dense/RRF/Bundling은 그 위에 얹는 품질 개선이다.

### 7.1 검색 전 Metadata 축소 (Metadata-First Filtering) — MVP 필수

전체 청크를 대상으로 바로 유사도 검색을 하지 않는다. `RetrievalQuery`를 만들 때 질의에서 **기업, 기간, 문서 유형(doc_group), 공시 subtype, 지표(fact_type), 연결/별도 기준**을 먼저 분석하고, `manifest.jsonl`의 해당 필드로 후보 문서를 좁힌 다음에야 검색을 수행한다. 예: "삼성전자 2025년 연결기준 매출액"이면 `corp_code="00126380"`, `doc_group="periodic"`, `rcept_dt` 2025 회계연도 대응 구간, `consolidation_basis="연결"`까지 먼저 필터링 — 4,204건 전체가 아니라 이미 좁혀진 수 건 안에서만 검색한다. `RetrievalQuery`에 이미 있는 `corp_names`/`doc_group_filter`/`doc_subtype_filter`/`date_range` 필드가 이 역할을 하며, 여기에 `fact_types`(지표)와 표의 `consolidation_basis`(연결/별도)까지 필터 신호로 명시적으로 사용한다.

### 7.2 계층형 Retrieval (문서 → 섹션 → 표/문단 → Evidence) — **MVP 필수 (등급 상향)**

전체 청크에 대한 단일 flat 검색을 하지 않는다. 4단계 funnel로 좁혀 나간다:

1. **문서 단계**: §7.1의 metadata 필터로 후보 `doc_id` 집합 확정
2. **섹션 단계**: 후보 문서 내에서 `Chunk.section_hierarchy`(§6-(1)에서 추가된 필드) 기준으로 질의와 관련된 섹션 후보 축소(예: "투자 계획"이라는 질의면 "설비투자현황" 섹션 우선)
3. **표/문단 단계**: 축소된 섹션 안에서만 실제 BM25/Dense 검색(§7.3) 수행
4. **Evidence 단계**: 검색된 chunk 안에서 구체적인 cell/문장 단위 evidence 확정

이 계층 구조가 있어야 `evaluation_strategy.md`의 Document Recall@k / Section Recall@k / Evidence Recall@k를 **단계별로 분리 측정**할 수 있고, 검색 실패가 어느 단계에서 발생했는지(문서를 못 찾았나, 섹션을 못 찾았나, 근거를 못 찾았나) 구분할 수 있다.

**MVP 필수로 상향한 근거 [확인]**: 코퍼스가 5.29GB(periodic XML 평균 3.44MB, 최대 30.7MB)이므로 전체 청크를 flat하게 훑는 검색은 정확도 이전에 **응답 지연·메모리에서 성립하지 않는다**. metadata로 문서를 수 건까지 줄이고 섹션→청크로 좁히는 구조는 "정확도 향상 옵션"이 아니라 **규모 대응 필수 설계**다. 더불어 계층형이 없으면 위 3개 Recall 지표를 측정할 수단 자체가 사라져, 검색 실패의 원인 분석이 불가능해진다.

### 7.3 하이브리드 검색: BM25(MVP 필수) + Dense + Metadata, RRF로 결합(가능하면 MVP에 추가)

**BM25(어휘 매칭, "매출액"·"유상증자" 같은 정확한 용어에 강함)를 전체 코퍼스(4,204건 / 5.29GB)의 최소 검색기로 채택한다 — 이것이 MVP 필수다.**

**[확인] 엔진 선택 제약**: 코퍼스가 5.29GB(periodic 5.05GB)이므로 `rank_bm25` 같은 **순수 파이썬 인메모리 BM25는 이 규모에서 부적합**하다. **SQLite FTS5 / Tantivy / Lucene(또는 Elasticsearch·OpenSearch) 계열의 디스크 기반 역색인**을 써야 한다. 어떤 엔진을 쓸지는 첫 회의에서 확정한다(`meeting_decisions.md`) — 이 결정이 Week 1 전체 색인 성공 여부를 좌우한다.

여기에 Dense Retrieval(의미 매칭)을 더하고 Metadata Retrieval(§7.1, 항상 우선 적용)과 결합하는 것은 **"가능하면 MVP에 추가"** 등급이다.

**[확인 — 주최 측 공식 답변] Dense Retrieval 규정·모델·범위**:
- **허용 여부**: Dense Retrieval은 규정상 허용. 임베딩 모델은 HyperCLOVA X에 한정되지 않고 **BGE-M3, multilingual-e5 등 사전학습 임베딩 모델 사용 가능**. 단 임베딩·검색 대상은 제공 코퍼스로 제한하고 **최종 답변 생성은 HyperCLOVA X만** 사용(생성 단계와 검색 단계의 모델 제약이 다르다는 점이 핵심).
- **적용 범위(단계적)**: 전체 5.29GB에 일괄 적용하지 않는다. **1단계 — periodic의 사업내용(사업의 개요·주요 제품 및 서비스)·원재료 및 생산설비·위험요인·연구개발활동 섹션**부터 BM25+RRF로 결합 적용. **2단계 — 1단계에서 Recall 개선이 실측으로 확인된 뒤에만** 다른 섹션·doc_group으로 확대. 확대 여부를 "여유 있으면"이 아니라 **"측정된 효과가 있으면"**으로 게이팅하는 것이 이전 버전과의 차이다.

결합 방식은 **RRF(Reciprocal Rank Fusion)를 기본안으로 우선 채택**한다 — 학습(fine-tuning, 가중치 튜닝)이 필요 없고 구현이 단순하다(`score(d) = Σ 1/(k + rank_i(d))`, 각 검색기의 순위만 있으면 됨, 관례상 `k=60`). Cross-Encoder Re-ranking 같은 고비용 고도화는 §9(Post-MVP)로 분리한다. **일정이 부족하면 Dense 확대(2단계)부터 줄이고, 1단계 범위·BM25 전체 커버리지·계층형 축소는 절대 줄이지 않는다.**

### 7.4 Context Bundling (구조적 결합, 고정 윈도우 아님) — 가능하면 MVP에 추가

검색된 chunk를 그대로 근거로 쓰지 않고, **구조적으로 관련된 주변 정보**를 함께 묶어 근거를 완성한다:

- 표(TABLE) chunk가 검색되면: 그 표의 `table_metadata`(제목, 행/열 헤더, 단위, 기준기간, 연결/별도)를 항상 함께 첨부한다 — 셀 값만 보여주면 "무엇의 얼마인지" 맥락이 사라진다.
- 문단(PARAGRAPH) chunk가 검색되면: 같은 `section_hierarchy`를 가진 섹션 제목과, **논리적으로 이어지는 문단**(예: 같은 번호매김 항목의 연속)을 결합한다.
- **단순히 앞뒤 index ±N개 청크를 무조건 붙이지 않는다** — 그 청크가 실제로 같은 섹션/같은 표/같은 논리 단위에 속하는지 `section_hierarchy`·`table_metadata`로 판단한 뒤에만 묶는다. 무관한 인접 청크를 섞으면 근거완전성은 늘어 보이지만 근거기반(hallucination 방지) 평가에는 오히려 해가 된다.

## 8. 계산 원칙 재확인 (Python Calculator, HyperCLOVA X는 설명만)

금액 파싱, 단위 정규화(억원↔백만원↔원), 합계, 차이, 증감률, 비율, 기업 간 비교는 **전부 Python Calculator가 수행**하고 그 결과를 `CalculationRecord`에 담는다. **HyperCLOVA X는 이미 계산된 `CalculationRecord`의 결과와 근거(evidence)를 자연어로 설명하는 역할만 한다 — 숫자를 다시 계산하거나 재추정하지 않는다.** 이는 기존 계획의 "금액/계산은 Python" 원칙과 동일하지만, Hybrid로 확장되며 Calculator가 다루는 연산 범위(합계·차이·증감률·비율·비교)를 명시적으로 확정한다는 점이 다르다 — `team_workstreams.md`의 C 담당 범위에 반영.

**RAG(EVIDENCE_SUMMARY) 경로 답변의 숫자도 예외 없이 원문 Evidence와 대조한다.** FACT_LOOKUP을 거치지 않고 HyperCLOVA X가 검색된 문단에서 숫자를 인용해 서술할 때도(예: Q2의 투자계획 요약 중 금액이 언급되는 경우), Verifier가 그 숫자가 `retrieved_context`의 실제 텍스트에 존재하는 값인지 문자열/정규식 수준으로 대조한다 — 일치하지 않으면 hallucination으로 플래그하고 답변에서 제거하거나 "확인되지 않음"으로 대체한다. 즉 Calculator가 만든 숫자든 RAG가 인용한 숫자든, **답변에 나가는 모든 숫자는 근거 대조를 통과해야 한다.**

## 9. MVP 이후 확장 (Post-MVP)

아래 두 항목은 **검색 품질을 한 단계 끌어올리는 유효한 기법이지만, MVP 필수 요건은 아니다.** §7.3의 BM25+Dense+RRF 베이스라인이 안정화된 뒤, 여유가 있을 때(`development_roadmap.md`의 buffer 구간 또는 예선 통과 후) 검토한다.

- **Cross-Encoder Re-ranking**: BM25+Dense+RRF로 추린 1차 후보군을 질의-문서 쌍 단위로 정밀 재정렬. 정확도는 높아지지만 추론 비용이 커 응답 지연시간에 영향 — 지연시간 여유를 확인한 뒤 도입.
- **Query Decomposition**: 복합 질의를 하위 질의로 자동 분해(예: Q6의 "2023년 사업보고서와 2025년 사업보고서 비교"를 "2023년 핵심사업 조회" + "2025년 핵심사업 조회" + "비교"로 분해). 지금은 Task Router가 질의 유형 분류와 route 조합까지만 하고, 진짜 sub-query rewriting은 하지 않는다 — `TaskPlan.steps`로 이미 다단계 실행은 가능하므로, 자동 분해가 없어도 사람이 손으로 짠 route 조합 규칙(예: "비교" 키워드 감지 시 두 개의 FACT_LOOKUP + 하나의 MULTI_DOCUMENT_ANALYSIS)으로 MVP는 충분히 커버 가능.

## 10. 실험 트랙 (Research Track — 게이팅 조건 있음)

아래 4개는 **내부 평가 데이터와 검색 실패 로그가 충분히 쌓인 이후에만** 실험 대상으로 고려한다. 지금 시점(eval set 자체가 없음)에 시도하는 것은 시간 낭비 위험이 크므로 5주 로드맵에는 포함하지 않는다.

- **Hard Negative 학습**: 리트리버(Dense 임베딩 모델) 파인튜닝에 필요 — 자체 학습 인프라와 상당량의 (질의, 정답문서, 오답이지만 유사한 문서) 삼중쌍 데이터가 전제. 지금 팀 규모·일정에서는 스코프 아웃.
- **HyDE(Hypothetical Document Embeddings)**: 질의로 가상 문서를 LLM이 생성해 그 임베딩으로 검색 — **[확인]** 임베딩 모델 자체는 이제 자유롭게 쓸 수 있지만(BGE-M3 등), 가상 문서를 "생성"하는 단계는 여전히 HyperCLOVA X만 써야 하므로 검색 파이프라인 안에 생성 호출이 추가로 끼어드는 구조 자체는 유지된다. 검증 안 된 효과 대비 호출 비용·지연시간 증가가 부담이라 여전히 실험 트랙.
- **Dynamic N-shot Prompting**: 질의 유형별로 few-shot 예시를 동적 선택 — 필요성 자체가 실패 로그를 보고 판단해야 함(지금은 프롬프트가 몇 개인지조차 정해지지 않음).
- **DPO Re-ranker**: 선호도 학습 기반 리랭커 — 학습 데이터·인프라 요구가 가장 크다. 완전히 스코프 아웃, 결선 진출 시에만 재검토.

**원칙**: 이 4개를 "언젠가 하면 좋은 것" 목록에 넣어두되, MVP 로드맵(`development_roadmap.md`)의 어떤 주차에도 배치하지 않는다 — 배치하는 순간 5주 일정을 위협하는 과잉 설계가 된다.
